# D3D training and progressive layer pruning

The authors' `d3d_release` training implementation is integrated into `train/`
and `pruning/`. The existing single-request, concurrent, and SGLang inference
paths remain unchanged. The original release's duplicate evaluation code,
figure, and paper PDF are not copied into this repository.

## Separate training environment

Training and inference have different dependency pins. Do not install
`requirements.txt` and `requirements-train.txt` into the same environment.

```bash
python3.11 -m venv .venv-train
source .venv-train/bin/activate
pip install -r requirements-train.txt
pip install -e . --no-deps
```

The training release pins PyTorch 2.8.0, Transformers 4.57.3, Accelerate 1.12.0,
and TorchAO 0.13.0. Install a host-compatible PyTorch 2.8.0 CUDA wheel if needed.
The launcher's default attention backend additionally requires:

```bash
pip install flash-attn==2.8.3 --no-build-isolation
```

Alternatively pass `--attn-implementation sdpa` to avoid FlashAttention.
SDPA does not make the distributed training launcher a CPU training command.
The training model implementation lives in `models/d3d_training/`; inference
continues to use `models/d3d/` and its original environment.

## Training data

Prepare UTF-8 JSONL with one target-generated conversation per line:

```json
{"id":"example-0","status":"success","conversations":[{"role":"user","content":"What is 2 + 2?"},{"role":"assistant","content":"4"}]}
```

`messages` is also accepted in place of `conversations`; ShareGPT-style
`from`/`value` fields with `human`/`gpt` roles are normalized. Assistant
`reasoning_content`, when present, is passed to the tokenizer chat template.
The last assistant turn is supervised; earlier turns form its prompt.
Rows whose `status` is neither absent nor `success` are skipped. Examples
exceeding the configured prompt/sequence limits or lacking enough response
tokens are also skipped. Generation success is not a correctness guarantee.

Use responses generated by the intended target and its tokenizer. Keep
validation/test prompts disjoint from training prompts. Formal experiments
should use at least 32,768 distinct training examples/prompts; repeated epochs
or extra anchors from one prompt do not replace distinct examples. Smaller
runs are smoke tests, not evidence of method effectiveness.

## Offline training

Start with local copies of the initial Qwen3 draft checkpoint and target
tokenizer. The draft loader stages local checkpoint files together with the
training model code; it does not download a Hub draft ID automatically.

```bash
export DRAFT_MODEL=checkpoints/Qwen3-1.7B
export TARGET_MODEL=checkpoints/Qwen3-8B
export DATA_PATH=data/train.jsonl
export OUTPUT_DIR=outputs/d3d_b16_a128

CUDA_VISIBLE_DEVICES=0,1 NUM_GPUS=2 bash scripts/train.sh \
    --attn-implementation sdpa --disable-wandb
```

`TARGET_MODEL` in this launcher selects the tokenizer; the default CE objective
uses saved target responses and does not load a live target model. KL objectives
additionally require an explicit `--target-model` argument.

The launcher defaults to block size 16, 128 anchors per example, position-decayed
CE plus an AR loss, BF16, FSDP2, and gradient accumulation of 8. It defaults to
four GPUs unless `NUM_GPUS` and `CUDA_VISIBLE_DEVICES` are overridden. These are
release defaults, not a guarantee that a particular model/sequence length fits
on any two GPUs. Extra CLI arguments follow the defaults and override them:

```bash
bash scripts/train.sh --help
bash scripts/train.sh --block-size 32 --parallel-anchors-per-example 64 \
    --loss-decay-gamma 15.5 --gradient-checkpointing --disable-wandb
```

Set `PY` to choose the launcher interpreter and `MASTER_PORT` to change the
distributed port. For W&B, omit `--disable-wandb` and use `wandb login` or
`WANDB_MODE=offline`; do not put credentials in scripts.

Saved checkpoints include the model configuration and training-compatible
remote code. Use the existing inference environment to evaluate the resulting
local checkpoint with the normal `--drafter` / `--draft` flags. This integration
does not claim GPU training convergence or benchmark improvements.

## Progressive layer pruning

Each cycle removes one decoder layer: `select → prune → train → choose`.
Start from a trained local D3D checkpoint and repeat from the selected recovery
checkpoint until the desired depth is reached.

Selection and checkpoint validation use separate fixed tokenized datasets
(`.parquet`, `.jsonl`, or `.json`) with `prefix_ids` and `target_ids`. Optional
columns are unique `analysis_id` and `split`. `prefix_ids` contains the causal
context; `target_ids` starts with the visible anchor and contains at least one
full draft block. The default block size is 16. Token IDs must match the target
tokenizer; they are not free-form text or token IDs from another tokenizer.

With a `split` column, the defaults select `layer_selection` and
`layer_validation`, respectively. Without it, the whole provided file is used.
Both commands expect 512 rows by default; set `--expected-samples` explicitly
for a different fixed split size.

```bash
export PARENT=outputs/d3d_b16_a128/step-5000
export CYCLE=outputs/pruning/cycle-01

bash scripts/prune.sh select \
    --parent "$PARENT" --examples data/layer_selection.parquet \
    --output-dir "$CYCLE/selection" --devices cuda:0 cuda:1

bash scripts/prune.sh prune \
    --selection "$CYCLE/selection/selection.json" \
    --output "$CYCLE/pruned"

CUDA_VISIBLE_DEVICES=0,1 bash scripts/prune.sh train --nproc-per-node 2 \
    --student "$CYCLE/pruned" --dataset "$DATA_PATH" \
    --output-dir "$CYCLE/recovery" --max-steps 1000

bash scripts/prune.sh choose \
    --run-dir "$CYCLE/recovery" --examples data/layer_validation.parquet \
    --output-dir "$CYCLE/chosen" --devices cuda:0 cuda:1
```

The example step count and checkpoint path are illustrative, not a reproduced
paper training budget. Recovery uses FSDP2 and the full-depth teacher recorded
in the pruning provenance. Its default 8-bit AdamW implementation comes from
TorchAO; use `--optimizer adamw` for standard AdamW. Preserve the teacher
checkpoint and metadata between stages. Selection/pruning commands refuse
to overwrite existing outputs.

Checkpoint choice writes `selected_checkpoint.json`, including
`selected_checkpoint`, rather than copying weights into a new merged checkpoint.
Use that selected path as the next cycle's parent or as the inference draft.

## Code map

| Path | Role |
|:---|:---|
| `train/train.py`, `train/trainer.py` | Distributed offline training entry point and loop |
| `train/dataset.py`, `train/blocks.py` | Conversation loading and packed anchor-conditioned blocks |
| `train/losses.py`, `train/objective_kernels.py` | CE/KL, position weighting, and auxiliary objectives |
| `train/runtime.py`, `train/model_utils.py` | FSDP, checkpoint/code staging, and model helpers |
| `train/trajectory.py` | Optional trajectory-distillation utilities; disabled by default |
| `pruning/` | Layer selection, weight remapping, recovery, and validation |
| `models/d3d_training/` | Qwen3-derived training model and checkpoint auto-map template |
| `models/token_ids.py` | Checkpoint mask-token convention and validation |

The Qwen/Hugging Face attribution in the imported model files is preserved;
see [third-party notices](../THIRD_PARTY_NOTICES.md).
